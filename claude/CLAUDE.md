# Conventions

## プロジェクト横断参照

開発は `~/src`、資料（スライド・会議録・抄録・講義）は `~/Documents` にあり、
同じ案件が両方に散らばっている。名前が出たら以下で実体を解決すること。

実体は3箇所に分かれている:
- `~/src` … コード（ghq レイアウト `~/src/github.com/<org>/<repo>`）
- `~/Sync/Projects` … データ・実験成果物
- `~/Documents` … 資料（スライド・会議録・抄録・講義）

解決手順:
1. **`~/.claude/project-mapping.md` を最初に引く。** 載っていればそのパスを使う。
2. 載っていなければ 3箇所を検索して実体を特定する（`rg -il '<名前>' ~/Documents` 等）。
   ただし `vision` `app` `tools` `chat` `VLM` `tt` のような一般語は grep が誤爆するので、
   ヒットを鵜呑みにせず中身を確認する。
3. **どの場合も推測でパスを書かない。** 実装の話は解決したパスの実コードを読んでから答える。

@~/.claude/project-mapping.md

## `,` 始まりのディレクトリ（プロジェクトごとのメモ置き場）

各プロジェクトの root にある `,` 始まりのディレクトリは、私(ken)個人の作業スペース。
global gitignore (`,*/`) で ignore 済み。Claude Code はこれらを前提として把握しておくこと。

- `,` … ちょっとした ignore の書き捨てスクリプトやチェック用ファイルの置き場（throwaway/scratch）
- `,links` … 他プロジェクトへのシンボリックリンク。**全プロジェクトには張っていない**ので、
  無いことを「関連が無い」と解釈しないこと（横断参照の主手段は上記の検索）
- `,docs` … メモ・ドキュメント置き場

活用方針:
- `,links` の中身は他プロジェクトの参照なので、書き方や実装パターンを調べる材料として読んでよい
- `,` 配下は書き捨て前提。ここのスクリプトやメモを正式な成果物と混同しない
- これらを git にコミットしない（ignore 済み）

## 作業の進め方

**既定は「分ける」。** ken は1メッセージで複数の依頼をまとめて投げてくる。それを1本の流れで
順にやると必ずパンクする（ken 指摘 2026-09-01）。依頼が来たらまず**独立性で切り分け、
独立している分はサブエージェントに振る**。順にやるのは、依存があるときだけ。

- **メインセッションは振り分けと統合に徹する。** ken との対話・作業の切り分け・結果の統合と
  報告を持つ。実装そのものは自分で抱えない（抱えると ken の次の指示に応答できなくなる）。
- **切り分けの単位は「関心・触るディレクトリ」。** worktree は必須ではない。同じワーキング
  ツリーでも、触る範囲が重ならないように割り当てれば並行できる。各エージェントには
  「触ってよい範囲」と「絶対に触らない範囲」を**明示して**渡す。
- **同じファイルを触る作業は同じエージェントに束ねるか、直列に回す。** 分けた気になって
  同一ファイルで競合するのが一番損。
- **BE/FE の契約面（DB スキーマ・API スキーマなど）を触る作業は直列**（衝突コストが並列ゲインに
  勝つ）。触るのは1エージェントだけにし、追従は完了後に別エージェントへ振る。
- **共有資源を使う作業は1エージェントに限る**: テスト DB・ブラウザ（Claude in Chrome）・
  dev サーバー。同時に2つが触ると互いを壊す。
- **複数エージェント**: ken が並列作業のために Claude セッションを複数立ち上げることがある
  （同じ tmux session の別 window の `claude`）。サブエージェントでなく複数セッションで動く
  ときは、**window 一覧を見て**他の claude の存在を把握しておく。
- **編集がレースしたら**（同一ファイルの競合・push の衝突など）、相手セッションとの疎通
  （`tmux send-keys` でのメッセージ送信等）を試みてよいが、**疎通の前に必ず ken に確認する**。
  勝手に他セッションへ指示を送らない。

**判断に迷っても止まらない。** 無難な方を選び、根拠を残して（issue コメント・報告）先へ進む。
ken は後から方向修正する。事前確認が要るのは、どちらに倒しても手戻りが大きいときだけ。

## git

- **履歴破壊は禁止**（force push・`reset --hard` による公開履歴の書き換え）。
- **merge commit を作らない。** ブランチ / worktree を使ったら rebase して `git merge --ff-only`。
- 並行作業中の git は**明示パスのみ**: `git add <path>` だけを使い、**`git add -A` /
  `git commit -a` は禁止**（他エージェント・ken の書きかけを巻き込む）。push 前に
  `git pull --rebase`、弾かれたら再試行。
- **commit / push を自動でやってよいかはプロジェクトごと**（各 repo の CLAUDE.md に従う）。

## tmux 規約

各プロジェクトは専用の tmux session を持ち、開発サーバーはそこで動かす。session / window 名と
起動コマンドは各 repo の CLAUDE.md が持つ。

- **開発サーバーを Claude Code 内部の shell で起動しない**（foreground / background とも。
  ken がログを見られないため）。必ず担当 window で起動する。
- **作業開始時・環境を移動してきたときは各 repo の `/setup-tmux`**。冪等なので毎回叩いてよい。
- window の状態は `tmux list-windows -t <session> -F '#I: #W (#{pane_current_command})'`。
- サーバーログは `tmux capture-pane -p -t <session>:<window>` で読む。
- **サーバーが前面に居る window にスクリプトはキーを送らない**（コンパイルエラーで止まって
  いるのを踏み潰さないため）。ログを読んで直してから `--restart-*`。

## コーディングスタイル

- **インデントは触っているファイル・周囲のコードに合わせる。タブを強制しない**
  （Svelte にタブを強いると崩れる）。フォーマッタ設定があるプロジェクトはそれに従う。
- フロントのログは **loglevel**。`console.log` は見つけ次第置き換える。
- **迷ったら同じ repo / 姉妹 repo の同種コードを読んで同じ構成にする。** 新しいファイルを
  作る前に、既存を直せないかを見る。
